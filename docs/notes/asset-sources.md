# Asset & Geometry Sources — Reference Notes

Collected from a working Minecraft→Blender pipeline. Documents *where* each
kind of data comes from so we don't reinvent discovery later. Most of this is
already implemented in Project Bedrock; the entity-geometry trick (§3) is the
one genuinely new insight and is recorded here for the **future entity
rendering** feature (see `docs/PRD.md` "Future Roadmap").

## 1. World geometry — the player's local save

- Source: the world save folder (e.g. Java `DIM1/` for the End, or the
  overworld region dir). The `.mca` region files are parsed from scratch:
  - 4 KB header of per-chunk offsets
  - zlib-compressed NBT per chunk
  - `block_states` palette + bit-packed indices (the 1.18+ format)
- This yields the actual island/terrain geometry.
- Some block properties (e.g. torch `facing` values) need a *second* parse
  pass over the NBT.

> Project Bedrock already does this in `bedrock-parser` (region.rs, nbt_le.rs,
> chunk.rs). No action needed.

## 2. Textures, block models, item & particle sprites — the local client JAR

- Source: the installed Minecraft client JAR, read **as a zip** directly from
  `%APPDATA%\.minecraft\versions\<version>\<version>.jar` (Blender's Python can
  do this with `zipfile`; our Rust code uses the equivalent). Zero network
  download — the asset is already on the user's machine.
- From it we get:
  - Block textures (`end_stone.png`, `torch.png`, …) — real 16×16 pixels.
  - Block model JSONs (`models/block/*.json`) — define geometry as cuboids
    with per-face UVs (why e.g. a dragon egg looks right instead of a textured
    cube).
  - Item textures (sword, bow, arrow) for pixel-extrusion rebuilds.
  - Entity textures (enderman.png, enderman_eyes.png, dragon texture).
  - Particle sprites (`textures/particle/generic_0..7.png`).

> Project Bedrock already uses the JAR for textures + block-model JSONs
> (`JarTextureLoader`, `json_model.rs`, `assets_extractor.rs`). Note: some
> in-game tints (e.g. the purple particle tint) are applied *in code* by the
> game, not stored in the asset — replicate with a shader/Mix node on the
> Blender side; our extractor only provides the raw texture.

## 3. Entity geometry — Mojang's `bedrock-samples` repo  ⭐ the key trick

**Problem / dead end:** In *Java* Edition, entity models (ender dragon,
enderman, etc.) are **not shipped as files** — they are compiled into the
game's code. You cannot read them from the JAR or the world save.

**Workaround:** Mojang publishes Bedrock's entity geometry as open data in the
official `bedrock-samples` GitHub repository:

```
resource_pack/models/entity/*.geo.json
```

These JSON files contain the bone structure, pivots, and cube definitions.
Pair them with the **Java** entity *textures* from the local JAR (§2).

**Caveats when consuming the Bedrock `.geo.json`:**
- They use **legacy v1.8 conventions**.
- Pivots are stored with **Y flipped around 24**.
- Cube coordinates are **relative to the stored pivot**.
- Some parts (neck, tail on the dragon) are **procedurally generated by the
  game** and must be replicated manually — they aren't in the data file.

**Action:** When entity rendering is implemented, fetch geometry from
`bedrock-samples` and textures from the local Java JAR. Do not attempt to find
Java entity models in the JAR — they aren't there.
